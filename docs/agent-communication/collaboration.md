# Agent 协作实践指南

> 基于通信协议的实际协作流程和操作规范

## 审查工作流

当一个 Agent（如代码生成 Agent）完成工作后，另一个 Agent（审查 Agent）将对其工作进行审查。以下是审查流程的标准操作。

### 审查请求

工作 Agent 完成任务后，向 Orchestrator 提交：

```
1. 完成摘要（做了什么、改了哪些文件）
2. 变更列表（每个文件的具体改动）
3. 自评置信度（0-1）
4. 已知限制或待验证项
```

### 审查清单

审查 Agent 按以下清单逐项检查：

#### 代码审查

- [ ] **正确性**: 代码逻辑是否正确，是否解决了目标问题
- [ ] **安全性**: 是否存在命令注入、路径遍历等安全漏洞
- [ ] **健壮性**: 边界条件是否处理，错误路径是否覆盖
- [ ] **可维护性**: 命名是否清晰，结构是否合理
- [ ] **兼容性**: 是否适配目标平台（ARM64、CUDA 13.0、SM 12.1）
- [ ] **幂等性**: 重复执行是否安全

#### 文档审查

- [ ] **准确性**: 技术细节是否与实际一致
- [ ] **完整性**: 是否覆盖所有必要场景
- [ ] **可读性**: 目标读者能否理解
- [ ] **格式**: 是否符合项目文档规范

#### 脚本审查

- [ ] **可执行性**: 脚本是否可在目标环境直接运行
- [ ] **依赖**: 是否声明了所有外部依赖
- [ ] **回滚**: 失败时是否可安全回退
- [ ] **资源**: 是否会耗尽磁盘/内存/CPU

### 审查评分

| 分数 | 判定 | 后续动作 |
|------|------|----------|
| 90-100 | `approved` | 任务完成，可合并 |
| 70-89 | `approved-with-notes` | 任务完成，记录改进建议 |
| 50-69 | `changes-requested` | 返回 Worker 修改 |
| 0-49 | `rejected` | 需要重新设计 |

### 审查反馈格式

```markdown
## 审查报告

**任务**: [任务描述]
**判定**: [approved / changes-requested / rejected]
**评分**: [0-100]

### 通过项
- [列出做得好的方面]

### 需修改项
1. **[严重程度: major/minor]** [问题描述]
   - 文件: `path/to/file`
   - 建议: [具体修改建议]

### 建议项（非阻塞）
- [可选的改进建议]
```

## 实际协作示例

### 场景: 模型优化部署

以下展示三个 Agent 如何协作完成模型优化任务。

#### 阶段 1: 并行研究

```
Orchestrator 分发给三个 Worker:

Worker A (研究 FlashInfer):
  → 检查 GitHub issues
  → 查找 SM 12.1 相关 PR
  → 输出: 修复方案 + 预期效果

Worker B (研究 NVFP4):
  → 搜索 HuggingFace / ModelScope
  → 检查 RadixArk 官方渠道
  → 输出: 下载链接 + 使用说明

Worker C (研究 SGLang):
  → 查阅官方文档
  → 检查 GB10 兼容性
  → 输出: 安装步骤 + 配置参数
```

#### 阶段 2: 汇总决策

```
Orchestrator 收集三份报告:
  → 评估可行性和优先级
  → 制定执行计划
  → 分配执行任务
```

#### 阶段 3: 顺序执行

```
Step 1: Worker-infra 执行 FlashInfer 修复
  → 更新安装脚本
  → 上传到远程机器
  → 提交完成报告

Step 2: Worker-model 下载 NVFP4 模型
  → 使用 Worker B 发现的下载方式
  → 验证模型完整性
  → 提交完成报告

Step 3: Worker-engine 安装 SGLang
  → 创建虚拟环境
  → 安装依赖
  → 测试启动
  → 提交完成报告
```

#### 阶段 4: 交叉审查

```
Reviewer Agent 审查所有产出:
  → 检查脚本正确性
  → 验证文档准确性
  → 确认无安全漏洞
  → 输出审查报告
```

## 文件交换约定

### 目录结构

```
project-root/
├── docs/
│   ├── local-model/          # 模型部署文档
│   │   ├── quick-start.md    # 快速启动指南
│   │   └── full-manual.md    # 完整技术手册
│   └── agent-communication/  # Agent 通信文档
│       ├── protocol.md       # 通信协议规范
│       └── collaboration.md  # 协作实践指南
├── shell/                    # 部署脚本
│   ├── spark_vllm_start.sh
│   ├── spark_vllm_smart_start.sh
│   └── ...
└── logs/
    └── agent-comm/           # Agent 通信日志
```

### 命名规范

| 类型 | 命名格式 | 示例 |
|------|----------|------|
| 任务消息 | `msg-{task-id}-{type}.json` | `msg-001-task-assign.json` |
| 审查报告 | `review-{task-id}.md` | `review-001.md` |
| 状态文件 | `state.yaml` | 全局唯一 |
| 工作日志 | `YYYY-MM-DD.jsonl` | `2026-09-03.jsonl` |

## 注意事项

1. **不要启动模型**: 在所有准备工作完成之前，不要启动 vLLM 或 SGLang 服务
2. **验证后再执行**: 所有脚本先在本地验证语法，再上传到远程执行
3. **保留回退能力**: 每次修改前备份原始文件
4. **记录决策**: 重要的技术决策记录原因和备选方案
5. **中文输出**: 所有面向用户的文档和消息使用中文
