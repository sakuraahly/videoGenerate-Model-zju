# 阶段 3 — 任务自动完成（输出截断不再中断任务）

> 状态：计划(未实施) | 目标：当单轮回复被长度上限截断时，任务仍能自动续跑/续写到完成，而不是"半途中止等用户" |
> 主负责人：Agent/后端 | 依赖：book-03(输出行为) | 对后端影响：中 | 优先级：🔴 高

---

## 1. 问题背景（用户可见现象 + 事故）
- "agent 会在达到预设的输出内容长度之后终止输出，但是不会自动进行未完成的任务。"
- 追问："需要综合考虑现有项目文件对模型输出的限制是否合理，以及为什么不是按照预想的模型自然中断，而是输出内容超限强制中段。"

---

## 2. 根因分析

### 2.1 「预设输出长度」是什么
- `runs/agent/ctx_budget.py`：`MODEL_MAX_CTX_TOKENS=8192`（服务端 SGLang ctx 硬顶）、`REPLY_MAX_TOKENS=2048`（单轮回复预算）。
- `scheduler.py LLM_CFG.generate_cfg.max_tokens=2048`；`ui_app.run_turn` 也把 `REPLY_MAX_TOKENS` 写入 LLM 配置（`ui_app.py:203-206`）。
- 即：模型每次 completion 最多 2048 token。

### 2.2 为什么会被「强制中段」而非「自然中断」
- **自然中断**：模型在"我认为任务完成/需要用户输入/需要调用工具"时才停止——这是它**主动**的结尾。
- **强制中段**：模型**还没说完**（还在生成提示词/还在做多步工具推理/还在解释），就因为 2048 token 用尽而**被迫**截断——这是 `finish_reason=length`（或等价），不是自然结论。
- 为什么常被强制中段：本系统让 agent 在"一轮里"做太多事——理解创意 + 生成详细英文提示词 + 可能需要先调 `idea2prompts` + 再 `call_comfyui` 提交 + 汇报。这些步骤的**单轮产物**（尤其长英文提示词 + 工具调用参数 + 说明文字）极易超过 2048 token。
- 额外约束：ctx=8192 下，输入侧还要留下约 3.1k 固定开销 + 对话预算，能留给 completion 的本来就只有约 2k。所以不是"模型不会自然停"，而是"单轮内容被压缩到 <2k 才够，往往装不下完整工作流"。

### 2.3 为什么截断后「不会自动进行未完成的任务」
- `scheduler.py run_cli`：每轮收到用户输入后，`for chunk in bot.run(...)` 只取最后内容，然后**阻塞等下一次 input()**——截断后直接回落到"等待用户"，无自动续跑。
- `ui_app.py send`：有**自动续接**（`MAX_AUTO_CONTINUE=2`，`:469`；`needs_continuation`，`:581-585`），但条件较窄：要有文本、无中止标记（`⛔`/`不可恢复`/`熔断`）、**且没有已取到的 prompt_id**。若截断发生在"还没提交就停了"，或 `needs_continuation` 判定不满足，就不会续跑，用户被晾着。

---

## 3. 目标与范围

**目标**：让输出截断变成"自动续跑"的触发器，直到任务真正完成或必须问用户；同时评估 2048 上限是否合理、能否放宽。

**做**：
- 区分 `finish_reason`：识别"因长度截断"（`length`）vs "自然结束"（`stop`/工具调用），对截断自动续。
- 把自动续跑机制做稳：截断后自动补一个"继续完成刚才的任务"的 completion，并正确并入对话历史（不重复已做动作）。
- 放宽/调优 `REPLY_MAX_TOKENS`：若服务端 ctx 允许、且 `llm_mem` 常量同步，可适度上调；同时给出"每轮任务分治"原则——单轮只做"生成提示词"或"提交"或"汇报"，避免一轮塞满。
- 明确"自然中断"与"强制中段"的可观测区分（日志/状态行标记 finish_reason）。

**不做**：不把 ctx 硬顶盲目调大而破坏内存协同；不改"单轮回复精炼"的总原则（但要改成"分段+自动续"）。

## 5. 实施步骤

### 步骤 1：确认服务端/框架的 finish_reason 可达性
- 查 qwen_agent/SGLang 返回是否带 `finish_reason`（`stop`/`length`）或 `usage.completion_tokens` 等。记录结论。

### 步骤 0（2026-09-04 实机，阻塞）：**自动续接不得追加 role:system**

> **观察（2026-09-04 实机，仅记录不急着修）**：发送"你好"后出现 **两次** `[系统自动续接] 请继续完成当前任务。`——`needs_continuation` 只判定"有文本+无终止+无 prompt_id"，对**寒暄/已完整回答**也判续接，导致空转两轮。方向（已合入本册实施）：判别 **截断(未完)** vs **自然停(答完)** 后再决定是否续接；寒暄不再续接。 — book-03 §0 已修（改 role:user）；本册步骤 2 的"继续"系统消息一并照此，禁止 system 追加；`_err_hint` 对 one-system-message 400 给出正确建议。

### 步骤 2：给「截断」打标记并自动续
- 若 `finish_reason==length`：追加一个"继续"系统消息（如已存在 `[系统自动续接]`，可复用），再发一次 completion；循环上限（如 3~5）防死循环；超限则向用户说明"内容较长，已分成多段：需要我继续还是直接给最终结论？"。

### 步骤 3：放宽/调优上限并做「任务分治」
- 若确认服务端 ctx 可用更大（需改 `llm_mem.json`+`start_sglang_coexist.sh`+`ctx_budget` 三处同步），适度上调 `REPLY_MAX_TOKENS`；否则保持 2048，但把 agent 脚本改为"分轮小步"（提示词一轮、提交一轮、汇报一轮，靠自动续接串起来）。

### 步骤 4：验证自然中断 vs 强制中段
- 跑长任务日志，断言：出现 `finish_reason=length` 时自动续跑；出现 `stop`（自然结束）时不强行续；不再出现"截断后静默等待"的场景。

## 6. 验收标准

- [ ] 单轮回复被截断时，系统自动发起续跑并完成未完成步骤（最终给出 `TASK_SUBMITTED` 或 `LOCAL_OUTPUT`），用户无需手动补"继续"。
- [ ] 日志/状态行可见"本次为长度截断，已自动续跑 N 次"或 `finish_reason=length`。
- [ ] 任务分治后，单轮不再尝试"一个脑子里塞完整生成流程"而超限；每轮有明确单一目标。
- [ ] 评估结论（`REPLY_MAX_TOKENS` 是否调整及其依据）记录在 `docs/test-results/`。

## 7. 风险与回滚
- **风险：自动续跑造成重复动作**（重复提交/重复生成）——用 `turn_state`/`session_state` 的 task 记录与幂等判断防重；提交类动作成功即结束本轮，避免续跑重复提交。
- **风险：放宽 ctx/REPLY_MAX_TOKENS 破坏内存协同**——若动服务端 context_length，必须同步 `ctx_budget` + `llm_mem.json` + 启动脚本，否则 400。计划默认不调大 ctx，改走"分治+自动续"。
- **回滚**：自动续跑为可开关（常量控制）；随时可回退到"截断即停、用户说继续"。
