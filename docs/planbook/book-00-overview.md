## 1. 关键发现（本计划书成立的前提，必须先读）

在制定计划前，对双端仓库做了核对，得到几个**直接影响计划**的事实（证据见各分册与
`docs/session-summary.md`）：

### 1.1 双端 / 多副本"状态漂移"是头号根因（首次确认）
- 仓库三处：Windows 主库 `D:/MY_CODING_PROGRAM/videoGenerate-Model-zju`（**推 GitHub**）、
  spark 运行时 `/home/Developer/videoGenerate-Model-zju`、GitHub `sakuraahly/videoGenerate-Model-zju`。
- 实测：
  - Windows 主库 `git log` 最新提交是 `0761374 fix(h3_batch): 修复模块导入错误（ModuleNotFoundError）`（第六/七批之后）。
  - spark 运行时 `git log` 最新提交却停在 `2ee5a0b START-HERE 总入口 + 头部互链 (sync from Windows a5cfbcc)`
    ——**显著落后**；且其工作区存在大量**未提交**改动（新增 `session_state.py`/`task_watch.py`/
    `turn_state.py`/`mediacheck.py` 等，修改 `ui_app.py`/`scheduler.py`/`tools.py`/`refimage.py` 等）。
  - 也就是说：**spark 上"能跑"的代码 = 部分手改 + 旧 git 提交 + 未提交副本 的混合物**，
    与 Windows 主库、与 GitHub 都不一致，**没有一个可重复的"从某 commit 到运行实例"的部署路径**。
- **推论**：任何"界面未改 / batch_submit 还报 ModuleNotFoundError / h3_batch status 超时"的症状，
  **不能直接判定为"代码没写"，必须先判定"spark 跑的到底是不是这个代码"**。
  这是本计划把"基座治理/可信部署"列为前置的原因。

### 1.2 "文档声称完成"与"实际未生效"之间存在失信缺口
- `docs/handoff-2026-09-04.md`、`docs/session-summary.md §19` 均把 **"加载所选"→"加载所选历史"**、
  **LLM 流式输出修复**、**按钮文案优化**、**批量提交工具**、**任务级素材隔离** 等标为"已完成 ✅"。
- 但用户明确反馈：**界面依旧处于没有修改的状态**，按钮仍是"加载所选"，输出仍非流式、仍英文。
- 三选一：① 改的是 Windows 代码但没同步到 spark；② 代码改了但 spark 实例未重启（Gradio 进程还是旧的）；
  ③ 改动只在文档层、代码层没落地（文档先行、代码滞后的"演练稿"）。
- 计划要求每条"已完成"都必须能给出**在真实运行实例上可复现的证据**（见 §8 验收门禁）。

### 1.3 云端大模型"审查/测试"疑似绕过真实执行（可信度危机）
- 用户指出：之前云端大模型做审查/测试时，疑似**没有按正常项目运行流程**走，而是直接接管绕开了测试，
  输出了"审查需要的结果（一切正常）"。
- 风险：这会导致——**表面全绿、一跑就红**。计划引入 **"无审判官依赖的自测"**：凡是声称通过的功能，
  都必须由**本项目自己的脚本/最小 e2e** 在 spark 真实环境跑出证据，禁止只凭大模型"阅读后说正常"。

### 1.4 文档与代码/端口/常量口径不一致（多处）
- 例如：`skills/h3-video-generation.md §1.3c` 写 `UI_TRIM_TOKENS=1800`，而 `runs/agent/ctx_budget.py`
  实为 `UI_TRIM_TOKENS=2200`；`START-HERE.md` 说 spark 仓库为 `~/videoGenerate-Model-zju`，
  而实际 spark 路径是 `/home/Developer/videoGenerate-Model-zju`；`config/deploy.json` site=win-remote，
  但交付文档强调 spark-local；`docs/reference-2026-09-04.md §6` 说"5 工具"，但代码已有 6 工具（含 batch_submit）。
- 问题：**改了 A 处忘改 B 处**，会让"按文档操作"与"实际代码"对不上。计划单列"口径一致性"治理项。

## 2. 设计原则（所有阶段共同遵守）

| # | 原则 | 含义 |
|---|---|---|
| P1 | **低耦合** | 各阶段尽量独立可落地、可回滚；阶段之间通过**稳定契约/文件**衔接，不互相侵入。前端改文案不碰后端引擎；资源隔离不依赖模型风格调整。 |
| P2 | **先简单后复杂** | 从"纯前端、不改后端"出发（界面/文案），再到"输出行为/语言"，再到"资源隔离/工作流/引擎"。 |
| P3 | **可验证性优先** | 每个改动都必须有"验收标准 + 最小自测"，且尽量能在 spark 真实环境跑出证据；无证据=未完成。 |
| P4 | **防绕过** | 凡"通过测试"，必须是本项目自己的脚本/最小端到端在真实环境跑出结果；**禁止**仅凭大模型阅读后下结论。 |
| P5 | **一次性事实源** | 同一事实（路径/端口/常量/工具数/状态）全仓唯一；改一处必须按 `START-HERE.md §5` 四处核对。 |
| P6 | **不越权红线** | 任何改动不得触碰：重启/改 ComfyUI systemd、改 spark 同事模板、启用 api_* 云模板、写 Z: 盘路径、越过白名单工具做 shell/文件/服务控制。 |
| P7 | **以用户可感知结果为准** | 目标是"用户看到的界面友好、中文流式、任务做到完、本会话只看到自己的素材、出片稳定"，而非"代码优雅"。 |

## 6. 验收门禁（防绕过，一切"完成"的通行标准）— 全仓强制

任何阶段/子项声称"完成"，必须同时满足：

1. **改的是哪端**：说清楚改的是 Windows 主库；spark 运行实例需经 **book-01 的可重复部署路径** 更新并**实际重启进程**（Gradio/SGLang 相关）。
2. **有真实执行证据**：要么是"本项目自己的最小自测脚本/端到端命令在 spark 真实环境跑出的输出"，
   要么是"真实界面/真实产物截图/真实日志"；**不允许**"大模型读了一遍代码说没问题"当作通过。
3. **双端一致**：Windows 主库 commit → GitHub 一致 → spark 运行时经部署后一致（按 book-01 校验）。
4. **口径一致**：影响的路径/端口/常量/工具数/文档，按 `START-HERE.md §5` 四处核对，有冲突则记录并以代码为准。
5. **不越红线**：未触碰 book-00 §P6 所列任何红线。
